## 1. E2E 테스트

`tools/e2e/studio-e2e.js`는 앱을 화면 없이 실제로 띄워 피아노, Studio, AI 분석, 투어를 끝까지 사용해 보는 스크립트입니다. 항목마다 그 사이에 난 오류(창 오류, 처리되지 않은 Promise, `console.error`)를 모아 판정합니다.

```bash
MELOFI_SHOT=out MELOFI_SCRIPT=tools/e2e/studio-e2e.js MELOFI_USERDATA=out/ud npx electron .
```

## 5. 개선 사항

**AI 곡 분석(외부 오픈소스, 이 PC에서 실행)**
- **분리:** BS-RoFormer ep317(보컬), BS-Roformer-SW(6악기), Mel-Band RoFormer(리드 보컬/코러스), MDX23C DrumSep(킥, 스네어, 탐, 하이햇, 라이드, 크래시).
  - MUSDB18 기준(SDR): 드럼 10.89, 베이스 9.42, 그 밖 7.97, 보컬 12.4 dB.
- **박자·채보:** Beat This(박자·템포), Basic Pitch(채보), MuScriptor small/medium/large(약 35개 악기, 비상업 CC BY-NC 4.0 표기).
- **분석 창:**
  - 시작 전에 방식(분석 엔진, 악기 분리, 채보)을 드롭다운에서 고름.
  - 실시간 로그 창과 진행 막대 2개(현재 단계 / 전체).
  - 분석 전 GPU 확인: 모델별 필요 메모리, 사용률, 피아노 화면을 그리는 GPU. 2초마다 새로 읽음.
  - 단계별 예상 시간 표시.
  - 채보 방식만 바꾸면 분리와 박자 결과는 다시 쓰고 채보만 다시 돌림.
- **분석 결과 → 프로젝트:** 템포 맵, 오디오 트랙(악기별), 8마디 MIDI 패턴.

**Studio**
- FL Studio식 작업 흐름(98개 항목 모두 95% 이상)과 FL 용어.
- Riff Machine 단계별 창, Newtone식 음정 편집, Loop Starter와 루프 라이브러리, 신스 프리셋 28개.
- 분리되는 창, 사이드체인, 녹음 대기(arm), 박자표 마커, 포르타멘토, Ctrl+L, 믹서 트랙 패널.

**투어**
- 13강 78단계, 단계마다 애니메이션(42종), 강의 소개 카드.
- "FL Studio와 같은…" 비교 문구 제거.

**시작 카드**
- 로딩이 끝나면 피아노 / Studio 선택 화면으로 커짐: 상세 정보, 최근 작업, 오른쪽 위 프로필 → 계정 센터.
- 로딩 중 로그인 버튼 제거.

## 6. 남은 일 · 알려진 한계

- **마스터링:** FL Studio·큐베이스 기준 95% 유사도로 나중에 빌드하기로 함.
- **분석의 한계:**
  - 코드 인식이 아직 거침.
  - 짧은 곡(30초 이하)은 BPM을 두 배로 읽을 수 있음.
  - 간이 분석은 구간을 하나만 잡는 경우가 있음.
- **이미 저장한 프로젝트:** U1, U4 이전에 만든 프로젝트에는 잘못 잡힌 마디가 남아 있음. AI 분석 창에서 다시 만들면 됨(분석 결과가 저장돼 있어 바로 만들어짐).
- **E2E로 확인하지 못한 것:**
  - 실제 파일 저장/열기 대화상자, WAV/MP3/영상 내보내기 파일 쓰기, 마이크 녹음, VST, 보컬(NNSVS), 계정 서버, MIDI 장치. 대화상자나 장치가 필요해 자동 실행에서 빠짐.
  - 오디오 파형이 템포 맵을 따라 그려지는지는 직접 화면으로 보지 않았음.
- **GitHub:** origin은 `0af1200`에 머물러 있음. 새 커밋 push는 사용자가 직접 해야 함(현재 토큰에 권한 없음).

## 8. 4차: 앱 전체 전수 점검 (2026-11-14)

모든 테스트는 화면 없이(헤드리스) 임시 userData로 돌렸고, 사용자가 쓰는 MeloFi 창이나 설정은 건드리지 않았습니다.
헤드리스 실행에서는 파일 대화상자·탐색기·브라우저가 화면에 뜨지 않도록 main.js가 대신 "취소"로 답하고 기록만 합니다.

### 메모리 (사용자 요청: 메모리에 여유)

sweep이 앱의 모든 프로세스 메모리를 50검사마다 기록하고, GPU 프로세스 2GB·렌더러 4GB를 넘거나 처음보다 1.5배 넘게
커지면 실패로 봅니다(`test:metrics`). Studio 전체 sweep(약 700검사, 30분) 측정값:

| 프로세스 | 처음 | 끝 / 최고 |
|---|---|---|
| GPU | 380MB | 380~490MB, 늘지 않음 |
| 렌더러 | 2.9~3.2GB | 3.2~4.2GB, 오르내림(누수 아님) |

- 15GB까지 커졌던 GPU 프로세스(18:36, `scratchpad/udw/w9`)는 이 브랜치의 테스트가 아니었습니다(이쪽 테스트는 모두 `scratchpad/out/…/ud`). 같은 패턴은 재현되지 않았습니다.
- 렌더러가 큰 이유: 악기 샘플이 두 번 들어 있습니다. 메인 스레드의 디코드 캐시와, 채널마다 오디오 워클릿이 받은 복사본. 디코드 캐시 상한은 1.5GB → 1.0GB로 낮췄습니다(소리는 같고, 오래 안 쓴 악기를 다시 고르면 다시 디코드).
- 테스트는 한 번에 무거운 인스턴스 하나만 돌리고, 시스템 RAM이 75%를 넘으면 즉시 끄는 감시를 붙였습니다. 두 번 다른 프로세스 때문에 RAM이 95% 넘게 튀어 테스트가 꺼졌습니다.
- **샘플 공유 (2026-11-15)**: 앱 페이지와 스크립트를 cross-origin isolated로 열고(`Cross-Origin-Opener-Policy: same-origin`,
  `Cross-Origin-Embedder-Policy: credentialless` — 깃허브·디스코드 프로필 사진 같은 외부 그림은 그대로 뜸), Studio 악기 샘플을
  SharedArrayBuffer에 둡니다. 워클릿(채널마다, 오프라인 렌더마다)은 복사본 대신 같은 메모리를 읽습니다. 격리가 안 되는 환경에서는
  예전처럼 복사로 동작합니다.

  | 케이팝 템플릿 + 같은 악기 채널 2개 더 | 공유 없음 | 공유 |
  |---|---|---|
  | 채널 6개 | 757~783MB | 673~732MB |
  | 채널 8개 | 862~1166MB | 778~807MB |
  | 오프라인 렌더 뒤 | 1264~1312MB | 848~917MB |

  전체 Studio sweep(729검사, 한국어·다크)도 메모리 검사까지 끝까지 통과: 렌더러 2.1GB → 2.7GB(전에는 2.9 → 4.2GB), GPU 프로세스
  436~514MB, 시스템 RAM 최대 59%.

  소리: 샘플러만 쓰는 프로젝트를 공유 켬/끔으로 렌더해 표본 단위로 비교하면 최대 차이 0.00003(약 -90dBFS, 덧셈 순서에서 오는 오차와
  같은 크기)으로 들리지 않습니다. 같은 모드에서 두 번 렌더한 차이는 최대 3e-8입니다.

userData에 두어 사용자의 실제 캐시는 건드리지 않았습니다.

남은 것 (다른 세션 담당 영역이라 고치지 않고 기록만 함):
- **GPU 80% 제한**: 분리 구간에서 GPU가 일할 때의 10초 표본 평균이 90%(47개 중 37개가 80% 초과)였습니다. 전체 평균은 56%,
  GPU 메모리는 최대 3.1GB/8GB. 지속 부하를 80% 아래로 묶으려면 `tools/stems/gpu_cap.py`의 쉬는 비율을 더 키우거나 분리 모델
  호출 밖의 작업(STFT 등)도 쉬게 해야 할 것 같습니다.
- **변환 중 메모리**: 곡 하나를 변환하면서 렌더러가 최대 5.2GB, 가사·보컬 파이썬이 3.6~5.6GB, 메인 1.8GB까지 커져 앱 전체가
  약 10GB를 씁니다. 다른 세션들과 겹치면 시스템 RAM이 75%를 넘어 이 테스트가 두 번 감시에 걸려 멈췄습니다(보컬 합성 이후 단계).
  16GB PC를 생각하면 줄일 필요가 있습니다.
- 보컬 음정: `check_sing.py` 기준 중앙값 20센트지만 음표 가운데 절반이 50센트 안에 드는 것은 678개 중 339개(`ok: false`).
  받아 적은 음표 길이와 NNSVS의 길이 보정 차이로 보이며 따로 볼 일입니다.
