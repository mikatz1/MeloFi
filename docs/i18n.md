# Languages (한국어 / English)

MeloFi shows every window in Korean or English. The choice is `lang` in `settings.json`:
`system` (default), `ko` or `en`. `system` follows the OS: Korean on a Korean system, English
everywhere else. It is set from the piano's 설정 menu (and the settings sheet's 정보 tab), Studio's
옵션 menu and the start card. Windows switch at once: the piano, the start card, the instrument
picker and the on-screen keys re-render; Studio re-renders its panes and swaps the text of the parts
built once (toolbar, pane heads) in place. Native file dialogs and window titles follow on the next
dialog / window.

## Design: the Korean source text is the key

```js
import { t, tc, tdyn, N_ } from '../i18n/i18n.js';
t('저장')                                   // '저장' | 'Save'
t('{n}개 채널', { n })                       // en table: "{n}개 채널": "{n} {n|channel|channels}"
t('"{name}"을(를) 열었습니다.', { name })     // Korean: "피아노"를 / "기타"를 (particle picked)
tc('touch', '보통')                          // same Korean, other meaning: key "touch::보통"
tdyn(msgFromMainOrPython)                   // runtime text: exact entry, else entries with {…} as patterns
const KINDS = [['soft', N_('여리게')]];        // marked where defined, translated where shown: t(label)
```

English lives in `renderer/i18n/en/*.json` (`{ "Korean": "English" }`), one file per area so separate
work does not collide: `piano` (piano window, start card, picker, keys), `studio` (studio.js),
`studio-panels` (rack, roll, playlist, mixer, channel sheet, browser …), `studio-ai` (AI, MIDI
conversion, lessons, tour), `sound` (synth presets, effects, mastering, templates, engine labels),
`main` (main process, song analysis / vocal / engine progress), `instruments` (instrument
descriptions). There is no Korean table: Korean is the code itself.

Why the Korean text and not made-up keys (`menu.file`):

- **The code stays readable and the change stays small.** About 2,900 lines carry Korean UI text,
  most of it inline in Studio. Wrapping `'저장'` as `t('저장')` keeps every line where it was, so
  branches being worked on in parallel still merge; moving each string into a key table would
  rewrite every line twice and lose the context next to the code.
- **Nothing ever shows blank.** A missing English entry falls back to the Korean, and is listed by
  `tools/i18n-check.mjs` and by the e2e Hangul scan, so gaps are found, not hidden.
- **Text made outside the page translates too.** Progress labels from the main process and from
  `tools/stems/analyze.py` arrive as Korean strings; `tdyn()` looks them up (with `{…}` entries as
  patterns), so the Python side stays untouched.
- The cost: the same Korean word with two meanings needs a context (`tc`), and rewording Korean
  copy needs the English key renamed too. `tools/i18n-check.mjs` catches both mistakes.

The piano window's table `renderer/js/strings.js` keeps its structure (`T.menu.file`); its values
are the Korean keys, and `T` reads each through `t()` (`localize()`), so existing code did not change.

## Rules

- Never call `t()` at module top level or once in a constructor for text that stays on screen: it
  would freeze the language. Call it when rendering, or mark with `N_()` and call `t(x)` when shown.
- Whole sentences, not pieces: `t('{n}개 중 {k}개')`, never `t('개 중')`. Placeholders are `{name}`;
  the English text must use the same names (the check fails otherwise).
- English plurals: `{n|one|other}` in the English text: `"{n}개 노트": "{n} {n|note|notes}"`.
- Korean particles after a value: write `을(를)`, `이(가)`, `은(는)`, `과(와)`, `(으)로`, `(이)라`;
  `t()` picks the right form from the final consonant of the word in front (quotes are skipped).
- Instrument, preset, theme and song names are proper names and stay as they are. Descriptions
  (`model` / `use` in `instruments/*/manifest.json`) are translated by `t()` where they are shown.
- Content the user typed (project, channel and pattern names) is never translated.
- Static HTML: Korean text and `title` / `placeholder` / `aria-label` are keys too; `translateDom()`
  swaps them on load and on every change, and restores the Korean when switching back.
- `// i18n-ignore` on a line, or `// i18n-ignore-file`, tells the check a Korean literal is data
  (search words, lyrics phonemes) and not UI.
- Dates and numbers: `locale()` gives `ko-KR` / `en-US` for `toLocaleDateString` and `Intl`.
- Main process (`main.js`, `updater.js`, `report.js` …): `require('./i18n-main')` gives the same
  `t()`; it reads `lang` from settings.json and follows `settings:save`.
- Start-up: each window asks main once, synchronously (`i18n:boot` in preload.js), for the choice and,
  in English, the tables, so the first paint is already in the right language and no module has to
  wait on a top-level `await` (which would delay every window's scripts past `did-finish-load`).

## Checking

- `node tools/test-i18n.mjs`: the core (plurals, particles, contexts, patterns).
- `node tools/i18n-check.mjs [--list]`: keys without English, placeholder mismatches, Korean literals
  not wrapped, per file.
- `tools/e2e/i18n-e2e.js`: switches to English, opens every window, menu, sheet and dialog it can
  reach and fails on visible Korean (proper names and user content allowed), then switches back
  and checks Korean. Screenshots of the main screens in both languages.

  `MELOFI_SHOT=<out> MELOFI_SCRIPT=tools/e2e/i18n-e2e.js MELOFI_USERDATA=<tmp dir> npx electron .`
